## 1. 系統背景與設計動機

傳統加簽制度通常採用「先到先得」或「教授主觀判斷」兩種方式，前者不公平（趕早的學生不一定是最需要的），後者效率低且易引發糾紛。

本系統模擬一套以**學生學習狀況**為輸入、**迫切度分數**為輸出的自動分流機制，具體解決以下問題：

| 問題 | 解決方式 |
|------|---------|
| 大四必修加簽失敗導致無法畢業 | 決策樹給予最高分 (95–100)，優先排在佇列頂端 |
| 低年級學生與高年級搶同一堂必修 | 依年級+課程+學分三維評分，自動區分優先順序 |
| 教授需手動審核每份申請，耗時費力 | 系統自動排序，教授只需逐一按下「發放授權碼」 |
| 加簽名額公開透明不足 | 即時統計看板顯示總申請、錄取、候補與大四保障率 |

## 3. UI/UX 設計決策

### 3.1 視覺主題：學術公文紙張風

本系統的使用情境是「大學教務系統」，因此刻意選擇與高科技暗色系截然不同的**米白公文紙**風格，傳達「正式、學術、有公信力」的視覺語境。

| 設計元素 | 選擇 | 設計理由 |
|---------|------|---------|
| 底色 | `#f5f0e8` 米白 | 模擬舊式公文紙張，與校園行政氛圍契合 |
| 紙質紋路 | `repeating-linear-gradient` 水平細線 | CSS-only 模擬稿紙質感，不需要圖片資源 |
| 卡片陰影 | 雙層 `box-shadow` 偏移效果 | 模擬紙張疊放的立體感，非模糊陰影 |
| 主字體 | Noto Serif TC | 宋體系衫，強調正式感 |
| 輔助字體 | Noto Sans TC | 表單填寫，清晰易讀 |
| 資料字體 | JetBrains Mono | 學號、分數等程式化資訊 |
| 大標題 | 朱紅 `#c0392b` + 文字陰影 | 模擬「印章」或「公章」效果 |

### 3.2 三色語義系統

三種迫切等級使用**傳統東方色彩**而非螢光色：

```
朱紅 #c0392b  →  極度迫切 (HIGH)   → 警示、緊急、不可忽視
靛藍 #2c4a7c  →  中度迫切 (MEDIUM) → 穩重、需要關注
石綠 #4a6741  →  一般候補 (LOW)    → 從容、自然、次要
金色 #b8860b  →  已錄取            → 榮耀、成功、獎勵
```

此色系在整個 UI 中保持一致：決策樹節點高亮、分數 badge、佇列行底色、統計長條圖，全部共用同一套 CSS 變數。

### 3.3 互動設計細節

- **決策樹即時高亮**：送出申請後，畫面左側決策樹圖的走過節點會以對應顏色亮起，3 秒後自動淡出，讓使用者直觀理解分類依據
- **學號重複防護**：`Array.some()` 即時檢查，同一學號不得重複送出
- **名額雙向調整**：增加名額時自動將已標記「失敗」的學生恢復為「候補中」，體現動態重評的公平性
- **全部錄取快捷鍵**：`grantAll()` 一鍵將名額內的候補者全數錄取，適合 Demo 時快速展示
- **預熱示範資料**：頁面載入後自動注入 5 筆涵蓋不同組合的示範申請，讓評審立即看到排序效果

## 4. 核心演算法：決策樹評分

### 4.1 概念說明

本系統的決策樹與學餐系統最大的不同在於：**輸出不是類別（哪條佇列），而是一個連續的分數（10–100）**。這個設計讓優先佇列能做細粒度排序——兩位都是「中度迫切」的學生，可以因為子節點的判斷而得到不同分數，從而在候補隊中決出先後。

### 4.2 決策樹完整結構

```
                     ┌──────────────────────┐
                     │   📋 新加簽申請進入    │  ← 根節點
                     └──────────┬───────────┘
                                │
                     ┌──────────▼───────────┐
                     │   🎓 年級判斷         │  ← 特徵 1（主節點）
                     └──┬──────┬────────┬───┘
                         │      │        │
                    大四/延畢  大三    大一/大二
                         │      │        │
            ┌────────────▼─┐    │    ┌───▼──────────────┐
            │  課程屬性？   │    │    │  必修 + 學分不足？ │
            └──┬──────┬────┘    │    └──┬───────────────┘
               │      │         │       │ 是              │ 否
          必修  │  選修│通識      │  ┌────▼───┐      ┌─────▼──┐
               │      │         │  │LOW 45-58│      │LOW 10-44│
    ┌──────────▼─┐    └──→ MED  │  └────────┘      └────────┘
    │  學分狀況？  │    62-71    │
    └──┬──────┬──┘              │
       │      │                 │  ┌─────────────────────────┐
     低  正常/滿               │  │       大三分支            │
       │      │                 │  │  必修+學分低 → MED 78-89 │
  HIGH       HIGH               │  │  必修        → MED 66-77 │
  95-100     88-94              │  │  選修/通識   → LOW 40-59 │
                                │  └─────────────────────────┘
                                │
                  選修+學分低→ MED 72-87
                  通識/學分滿→ MED 62-71
```

### 4.3 分數區間設計原理

每個葉節點的分數使用**隨機整數區間**（`randInt(min, max)`）而非固定值，有兩個目的：

1. **模擬真實差異**：相同條件的兩個學生，實際上還有許多無法量化的因素（缺課記錄、教授評語等），以小幅隨機值體現這種不確定性
2. **避免完全並列**：防止大量學生分數相同，使次鍵排序（申請先後）成為唯一決勝依據，而失去了分數本身的意義

| 葉節點情境 | 等級 | 分數區間 | 設計邏輯 |
|-----------|------|---------|---------|
| 大四 + 必修 + 學分低 | HIGH | 95–100 | 最危急，接近滿分 |
| 大四 + 必修 + 學分正常 | HIGH | 88–94 | 高危但稍緩 |
| 大四 + 選修 或 學分低 | MEDIUM | 72–87 | 有急迫性但非必修 |
| 大四 + 通識 / 學分滿 | MEDIUM | 62–71 | 大四彈性較低 |
| 大三 + 必修 + 學分低 | MEDIUM | 78–89 | 高於一般大三 |
| 大三 + 必修 + 學分正常 | MEDIUM | 66–77 | 中等緊迫 |
| 大三 + 選修 / 通識 | LOW | 40–59 | 時間充裕 |
| 低年級 + 必修 + 學分低 | LOW | 45–58 | 特例保障，稍高 |
| 低年級 + 一般情形 | LOW | 10–44 | 最低優先 |

### 4.4 程式碼實現

```javascript
function classifyUrgency(grade, course, credit) {

  // ── 節點 A：大四 / 延畢生 ──
  if (grade === 'senior') {
    if (course === 'required' && credit === 'low')
      return { level: 'high', score: randInt(95, 100) };  // 最高優先
    if (course === 'required' && credit === 'normal')
      return { level: 'high', score: randInt(88, 94) };
    if (course === 'elective' || credit === 'low')
      return { level: 'medium', score: randInt(72, 87) };
    return { level: 'medium', score: randInt(62, 71) };   // 大四通識/學分滿
  }

  // ── 節點 B：大三 ──
  if (grade === 'junior') {
    if (course === 'required' && credit === 'low')
      return { level: 'medium', score: randInt(78, 89) };
    if (course === 'required')
      return { level: 'medium', score: randInt(66, 77) };
    return { level: 'low', score: randInt(40, 59) };
  }

  // ── 節點 C：大一 / 大二 ──
  if (course === 'required' && credit === 'low')
    return { level: 'low', score: randInt(45, 58) };  // 特例小保障
  return { level: 'low', score: randInt(10, 44) };    // 一般低年級
}
```

## 5. 資料結構：優先佇列

### 5.1 優先佇列 vs 一般 FIFO 佇列

| 特性 | 一般 FIFO 佇列 | 優先佇列 (Priority Queue) |
|------|--------------|--------------------------|
| 加入規則 | 永遠加在尾端 | 加入後依優先鍵重新排序 |
| 取出規則 | 永遠取出頭端（最早加入者） | 永遠取出頭端（優先鍵最高者） |
| 應用情境 | 學餐排隊、印表機列印 | 加簽候補、急診分流、CPU 調度 |

### 5.2 以 Array.sort() 模擬 Priority Queue

JavaScript 標準函式庫沒有內建 Priority Queue，本系統使用以下策略：

```
priorityQueue (Array)
  │
  ├─ Enqueue：push() 後立即 sort()
  │     新元素先放在尾端，排序後自動移到正確位置
  │     時間複雜度：O(n log n)
  │
  └─ Dequeue：找到第一個 status === 'waiting' 的元素，
        將其 status 改為 'granted'（原地修改，不移除）
        設計說明：保留已錄取/失敗者在陣列中，讓 UI 能完整顯示所有申請歷史
```

### 5.3 排序比較函式詳解

```javascript
priorityQueue.sort((a, b) => {
  // 主鍵：分數降冪（高分在前）
  if (b.score !== a.score) return b.score - a.score;

  // 次鍵：申請流水號升冪（同分時，先申請者排前面）
  // 體現「同等條件下先到先得」的公平原則
  return a.id.localeCompare(b.id);
});
```

**為什麼不用 Max-Heap？**

Array.sort 的優點是實作簡單、程式碼可讀性高，適合期末 Demo 展示用途。若系統要承載數千筆申請並追求效率，應改用 Max-Heap（每次 Enqueue/Dequeue 為 `O(log n)`），而非每次排序的 `O(n log n)`。

### 5.4 Dequeue 的「原地標記」設計

```javascript
function pqDequeue() {
  // 找到第一個尚在等待的申請（陣列已排序，第一個即最高優先）
  const idx = priorityQueue.findIndex(a => a.status === 'waiting');
  if (idx === -1) return null;

  // 不執行 splice/shift，改為原地修改狀態
  // 優點：UI 可以完整顯示申請歷史（錄取、失敗、候補同時呈現）
  priorityQueue[idx].status = 'granted';
  return priorityQueue[idx];
}
```

## 6. 申請物件資料模型

每筆進入優先佇列的資料為以下格式的 JavaScript 物件：

```javascript
{
  id:          'APP-0001',       // 流水號，補零至 4 位，用於次鍵排序
  sid:         'B11201234',      // 學號（唯一鍵，防重複申請）
  grade:       'senior',         // 'senior' | 'junior' | 'fresh'
  course:      'required',       // 'required' | 'elective' | 'general'
  credit:      'low',            // 'low' | 'normal' | 'full'
  level:       'high',           // 決策樹分類結果（迫切等級）
  score:       97,               // 迫切度分數 10–100（決策樹輸出）
  status:      'waiting',        // 'waiting' | 'granted' | 'failed'
  submittedAt: 1716019200000,    // Date.now()（未來可計算等待時長）
}
```

**`status` 狀態機：**

```
           submitApplication()
                  │
               'waiting'
              ╱         ╲
   pqDequeue()           quota 已滿
        │                    │
    'granted'            'failed'
                             │
                      增加名額時恢復
                             │
                          'waiting'
```

## 7. 主要函式流程

### 7.1 送出加簽申請

```
submitApplication()
    │
    ├─ 讀取表單輸入（sid, grade, course, credit）
    ├─ 驗證：必填欄位 + 學號重複檢查（Array.some()）
    ├─ 產生流水號（appCounter++）
    │
    ├─ classifyUrgency(grade, course, credit)
    │       └─ 回傳 { level, score }
    │
    ├─ 建立 application 物件
    │
    ├─ pqEnqueue(app)
    │       ├─ priorityQueue.push(app)       ← O(1)
    │       └─ priorityQueue.sort(compareFn) ← O(n log n)，維持優先順序
    │
    ├─ highlightDT(grade, course, credit, level)  ← 決策樹視覺高亮（3秒）
    ├─ renderQueue()                              ← 重繪佇列 UI
    ├─ updateStats()                              ← 更新統計看板
    └─ showToast(分類結果摘要)
```

### 7.2 教授發放授權碼

```
grantNext()
    │
    ├─ 檢查 (quota - quotaUsed) > 0
    │       否 → markFailedAll() + 顯示「名額已滿」橫幅
    │
    ├─ pqDequeue()
    │       ├─ findIndex(status === 'waiting') → 取得最高分候補
    │       └─ 設定 status = 'granted'，回傳該物件
    │
    ├─ quotaUsed++
    ├─ updateQuotaBar()         ← 進度條更新
    ├─ 寫入 grantLog（含時間戳）
    │
    ├─ 若 quotaUsed >= quota → markFailedAll() + 顯示截止提示
    │
    ├─ renderQueue()            ← 重繪（錄取行變金色背景，失敗行文字刪除線）
    ├─ updateStats()
    └─ showToast(錄取通知)
```

### 7.3 名額調整與失敗復活

```
onQuotaChange()
    │
    ├─ 讀取新名額值，clamp 至 [quotaUsed, 50]
    ├─ updateQuotaBar()
    │
    └─ 若新名額 > quotaUsed（名額擴增）
            └─ 將所有 status === 'failed' 的申請改回 'waiting'
               隱藏「截止」橫幅
               renderQueue() + updateStats()
```

## 8. 統計計算邏輯

### 總申請人數
```
total = priorityQueue.length
```
包含所有狀態（waiting + granted + failed），反映教授共收到多少申請。

### 已錄取人數
```
granted = priorityQueue.filter(a => a.status === 'granted').length
```

### 排隊中人數
```
waiting = priorityQueue.filter(a => a.status === 'waiting').length
```

### 大四畢業生保障率
```
seniorRate = 已錄取的大四生人數 / 所有大四申請人數 × 100%
```
此指標是本系統的核心 KPI，衡量系統是否真正優先保障了有畢業壓力的學生。若保障率接近 100%，表示系統運作正確。

### 迫切度分佈長條圖
```
各等級比例 = 各等級人數 / 總申請人數 × 100%
```
即時呈現本課程申請人的整體迫切度結構，協助教授判斷是否需要開放更多名額。

## 9. 與上一個系統的設計差異對照

本系統（加簽）與前一個系統（學餐訂單）都使用了「決策樹 + 佇列」，但在概念層次上有根本差異：

| 面向 | 學餐訂單系統 | 加簽系統（本系統） |
|------|------------|------------------|
| 決策樹輸出 | **類別**（分入哪條佇列） | **分數**（10–100 的連續值） |
| 佇列數量 | **3 條**平行佇列（Express / Priority / Standard） | **1 條**優先佇列（所有學生共用） |
| 佇列模型 | FIFO（各佇列內先來後到） | Priority Queue（按分數自動排序） |
| 排序時機 | 無需排序，入隊即分流 | 每次 Enqueue 後重新排序整條佇列 |
| Dequeue 結果 | 元素從陣列移除 | 元素原地修改 status，保留歷史 |
| 視覺呈現 | 三條水平捲動列 | 單一垂直排名清單 |
| 核心 KPI | 快速取餐率（防遲到） | 大四保障率（防無法畢業） |
| UI 主題 | 深色科技工業風 | 米白學術公文紙張風 |

## 10. 模組對照表

| 函式名稱 | 對應概念 | 時間複雜度 |
|---------|---------|-----------|
| `classifyUrgency()` | 決策樹分類器 → 輸出分數 | O(1) |
| `randInt()` | 分數隨機化工具 | O(1) |
| `pqEnqueue()` | Priority Queue 入隊 + 重新排序 | O(n log n) |
| `pqDequeue()` | Priority Queue 出隊（原地標記） | O(n) |
| `markFailedAll()` | 批量標記失敗 | O(n) |
| `submitApplication()` | 主入口：驗證 → 分類 → 入隊 → 渲染 | O(n log n) |
| `grantNext()` | 教授發放一個授權碼 | O(n) |
| `grantAll()` | 批量發放授權碼 | O(n²) 最差 |
| `onQuotaChange()` | 名額調整 + 失敗復活 | O(n) |
| `renderQueue()` | 優先佇列 UI 渲染 | O(n) |
| `updateStats()` | 統計看板更新 | O(n) |
| `highlightDT()` | 決策樹節點高亮動畫 | O(1) |
| `seedData()` | 預熱示範資料（IIFE） | O(k log k) |

## 11. 延伸改進方向

### 演算法層面

- **改用 Max-Heap**：目前 `Array.sort()` 每次 Enqueue 花費 `O(n log n)`，若申請人數龐大（如全校搶修熱門課），改用 Binary Max-Heap 可將 Enqueue/Dequeue 降至 `O(log n)`

- **多維加權評分**：目前決策樹的三個特徵（年級/課程/學分）是硬編碼規則，可改為加權公式：
  ```
  score = w1 × 年級分 + w2 × 課程分 + w3 × 學分分 + w4 × 歷史加簽失敗次數
  ```
  教授可動態調整各權重，適應不同課程屬性的排序需求

- **機率式公平保障**：在高分學生之間引入小幅隨機擾動，避免完全相同條件的學生因申請時間差幾秒就決定命運

### 工程層面

- **後端 API 整合**：以 Node.js + PostgreSQL 持久化儲存，支援多課程、多學期
- **學生端即時查詢**：WebSocket 廣播佇列狀態變更，學生手機可看到自己當前排名
- **教授審核覆蓋**：支援教授手動插入高優先或否決特定申請，覆蓋演算法決定
- **加簽申請截止時間**：設定申請期限，期限後自動鎖定佇列並通知所有候補者結果

### 公平性層面

- **申訴機制**：學生可附上說明，教授審核後可調整分數
- **隱私保護**：佇列看板中，僅顯示學號後四碼與年級，隱藏完整個資
- **歷史數據分析**：追蹤學生多學期的加簽申請歷史，作為評分參考，避免「慣性搶課」
