# 急診室分診系統
## Max-Heap × Queue 在醫療優先排程中的應用

---

## 一、生活場景背景

急診室每天面對數十甚至數百位病患同時湧入，病患的嚴重程度差異極大：從輕微擦傷到心肌梗塞，若採用「先來先看」的 FIFO 原則，可能造成危急病患因排隊而延誤治療。

**核心問題：如何在有限診間（資源）下，讓最危急的病患最先被處理？**

這正是 Max-Heap + Queue 排程問題的典型生活應用。

### 對應製造業題目的類比

| 智慧製造 | 急診室分診 |
|---------|-----------|
| CNC 機台 | 診間 |
| 產品型號 P? | 病患（姓名 + 病情）|
| 刀具冷卻週期 | 診間消毒冷卻週期 |
| 剩餘生產件數 | 緊急程度分數 |
| 機台 Idle 空轉 | 診間空著但全在消毒 |

---

## 二、資料結構角色說明

### Max-Heap（最大堆積）— 分診決策大腦

儲存所有等待就診的病患，依**緊急程度分數（Priority Score）** 排序。

```
Max-Heap 節點格式：{name, condition, severity, score}
score = 緊急程度分數（1~100）
```

**緊急分級（Triage Level）設計：**

| 等級 | 代碼 | 分數範圍 | 範例病情 |
|------|------|---------|---------|
| 危急 | P1 | 91–100 | 心肌梗塞、意識模糊 |
| 嚴重 | P2 | 61–90 | 骨折、呼吸困難 |
| 中等 | P3 | 31–60 | 高燒、腹痛 |
| 輕微 | P4 | 1–30 | 擦傷、輕度扭傷 |

Heap 頂端永遠是**分數最高（最危急）**的病患，系統自動保證危急病患插隊。

**Heap 動態變化過程（舉例）：**

初始 Heap（3 位病患候診）：

```
          陳先生(心梗, 97)
           /            \
  林女士(骨折, 74)    王小弟(高燒, 45)
```

取出陳先生就診後，Heapify Down：

```
          林女士(骨折, 74)    ← 自動浮頂
               |
          王小弟(高燒, 45)
```

新病患黃先生（呼吸困難, 88）掛號 → Heap Push → Heapify Up：

```
          黃先生(呼吸困難, 88)   ← 插隊至頂
           /                \
    林女士(骨折, 74)      王小弟(高燒, 45)
```

### Queue（佇列）— 診間消毒冷卻輸送帶

每位病患看診結束後，診間需進行消毒程序，才能接待下一位病患。

```
Queue 節點：(可解凍時間, 'room', 病患資料)
可解凍時間 = 當前時間 + 消毒冷卻週期 + 1
```

Queue 是 FIFO 結構，確保消毒完成的診間依序重新開放，不會插隊搶用。

## 三、每個 Time Slot 的完整執行步驟

```
┌──────────────────────────────────────────────────────┐
│  急診分診排程 — 每個 Time Slot 執行流程               │
│                                                      │
│  Step 1：診間消毒完成檢查（Queue → Heap）             │
│    └── 若 Queue.front 的解凍時間 ≤ 當前時間           │
│        → 診間消毒完成，可重新接診                     │
│        → 推入 Heap，繼續競爭下一位病患                │
│                                                      │
│  Step 2：分診決策（Heap 頂端 → 診間）                 │
│    ├── Heap 非空 → 取出緊急分數最高的病患              │
│    │   → 安排就診                                    │
│    │   → 診間進入消毒 Queue                          │
│    └── Heap 為空 → 診間 Idle（等待消毒完成）          │
│                                                      │
│  Step 3：time += 1                                   │
└──────────────────────────────────────────────────────┘
```

## 四、關鍵設計邏輯

### 為何不能用 FIFO 排候診？

若採 FIFO，先掛號的輕傷病患會比後到的心梗病患先看診，造成：
- 危急病患等待時間過長
- 醫療糾紛風險上升
- 違反醫療倫理（緊急優先原則）

Max-Heap 解決此問題：**任何時刻掛號的高分病患，均可立即插隊到 Heap 頂端。**

### 為何冷卻要用 FIFO Queue？

診間消毒有其物理順序：消毒人員依序進行，先消毒完的診間先開放。Queue 的 FIFO 性質完美對應這個物理限制，不能讓後消毒完的診間插隊搶先開放。

## 五、模擬器功能說明

### 可調整參數

| 參數 | 預設值 | 說明 |
|------|--------|------|
| 病患批次 | 20 | 本輪進入急診的病患總數 |
| 診間數 | 3 | 同時可接診的診間數量 |
| 消毒冷卻（分鐘）| 2 | 每次看診後診間消毒所需時間單位 |

### 顯示面板

| 面板 | 內容說明 |
|------|---------|
| Max-Heap 候診佇列 | 即時顯示所有候診病患，依緊急度排序，頂端以紅框標示 |
| 消毒冷卻 Queue | 顯示每個消毒中的診間，綠框代表消毒完成可接診 |
| 診療日誌 | 完整記錄每個 Time Slot 的接診或 Idle 事件 |

### 統計輸出

- 總病患數 / 已處理數
- 診間閒置次數（Idle）
- 整體診間稼動率（%）

## 六、實際醫療系統對應關係

```
演算法元件          急診室實體對應
──────────────────────────────────────────────
Max-Heap 頂端    ↔  分診台當下最危急的病患
Heap Push        ↔  護理師登錄新病患的緊急指數
Heapify Up       ↔  危急病患自動插隊，排到最前面
Heapify Down     ↔  取出危急病患後，次緊急者浮頂
Queue FIFO       ↔  診間消毒的實際完成順序
解凍條件         ↔  消毒燈滅、診間系統確認可接診
Idle             ↔  診間空著但全部在消毒中（浪費）
```

## 七、演算法與現實的延伸思考

### 動態插隊問題

若病患在等待過程中病情惡化（如血壓驟降），其分數應即時上升並在 Heap 中上浮。實際系統會設置定時器，每隔一段時間重新評估所有候診病患的分數，並執行 **Decrease-Key** 操作（等效於 Heapify Up）。

### 多診間並發問題

本模擬簡化為「每個 time slot 只安排一位病患」。實際上可擴展為每個 time slot 安排 n 位病患（n = 可用診間數），需從 Heap 連續 Pop n 次，分別送入 n 個不同診間，n 個診間各自維護獨立的消毒 Queue。

---

## 八、結論

急診室分診問題是 Max-Heap + Queue 在生活場景中最直觀的應用之一。Max-Heap 實現了「緊急優先」的醫療倫理，Queue 實現了「消毒順序合法」的物理限制。兩個資料結構各司其職，共同構成一個公平、高效、符合現實約束的醫療資源排程系統。
