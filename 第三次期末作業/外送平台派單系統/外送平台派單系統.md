# 外送平台派單系統
## Max-Heap × Queue 在動態物流調度中的應用

---

## 一、生活場景背景

外送平台（如 Uber Eats、Foodpanda）每天處理數萬筆訂單，騎手數量有限，訂單湧入速度卻不固定。若採單純 FIFO 排單，先下單的訂單永遠先被派，但一筆「快超時、高罰款」的訂單可能在排隊中錯過最佳配送時機，導致平台付出高額違約金。

**核心問題：如何動態決定騎手接下來要送哪一筆訂單，讓平台損失最小、客戶滿意度最高？**

### 對應製造業題目的類比

| 智慧製造 | 外送派單 |
|---------|---------|
| CNC 機台 | 外送騎手 |
| 產品型號 P? | 餐廳訂單（菜色 + 商家）|
| 刀具冷卻週期 | 騎手回程（返回待命區）週期 |
| 緊急度分數 | 超時罰款 + 距離加權 = 優先值 |
| 機台 Idle 空轉 | 騎手全在回程中，無人可派單 |

---

## 二、優先值設計邏輯

每筆訂單的優先值（Priority Score）由兩個因子組成：

```
優先值 = 超時罰款（元）+ 配送距離（km）× 3
```

| 因子 | 說明 | 權重設計理由 |
|------|------|------------|
| 超時罰款 | 訂單若未準時送達，平台須支付的違約金（10~100元）| 直接損失，權重高 |
| 距離加權 | 距離越遠，難以在短時間補救，越需提前派出 | 間接風險，×3 加權 |

優先值越高 → 在 Max-Heap 中越靠近頂端 → 越優先被派單。

## 三、資料結構角色說明

### Max-Heap（最大堆積）— 派單決策大腦

儲存所有「目前可以被派出」的訂單，依優先值排序。

```
Max-Heap 節點格式：{id, dish, store, fine, dist, priority}
```

**Heap 動態變化過程（舉例）：**

初始 Heap（4 筆訂單）：

```
             #1003 滷肉飯(優先值 103)
              /                    \
  #1001 珍珠奶茶(78)        #1005 壽司(61)
       /
  #1002 炸雞(45)
```

派出 #1003 後，Heapify Down，#1002(45) 移頂後下沉：

```
             #1001 珍珠奶茶(78)
              /               \
     #1002 炸雞(45)         #1005 壽司(61)
```

新訂單 #1008 麻辣鍋（優先值 95）湧入 → Heapify Up：

```
             #1008 麻辣鍋(95)    ← 插隊至頂
              /               \
     #1001 珍珠奶茶(78)      #1005 壽司(61)
           /
     #1002 炸雞(45)
```

### Queue（佇列）— 騎手回程冷卻輸送帶

騎手完成送達後，需要一段「回程時間」才能返回待命區接受新派單。

```
Queue 節點：(可接單時間, 'back', 騎手資訊)
可接單時間 = 當前時間 + 回程冷卻週期 + 1
```

多位騎手的回程依照完成送達的先後順序排隊，FIFO 確保先回來的騎手先重新接單。

## 四、每個 Time Slot 的完整執行步驟

```
┌────────────────────────────────────────────────────────┐
│  外送派單排程 — 每個 Time Slot 執行流程                 │
│                                                        │
│  Step 1：騎手回程完成檢查（Queue → Heap）               │
│    └── 若 Queue.front 的可接單時間 ≤ 當前時間           │
│        → 騎手返回待命區，重新進入可用狀態               │
│        → 推入 Heap，參與下一筆派單競爭                  │
│                                                        │
│  Step 2：派單決策（Heap 頂端 → 騎手）                   │
│    ├── Heap 非空 → 取出優先值最高的訂單                  │
│    │   → 指派給最先恢復待命的騎手                        │
│    │   → 騎手進入回程 Queue                             │
│    └── Heap 為空 → Idle（等待騎手回程）                 │
│                                                        │
│  Step 3：time += 1                                     │
└────────────────────────────────────────────────────────┘
```

## 五、關鍵設計邏輯

### 為何罰款高的訂單要優先派？

若罰款高的訂單持續在 Heap 中等待，等到訂單超時後，平台實際損失的金額 = 罰款金額。因此，最大化「避免罰款」等同於最大化「派單優先值之和」，而 Max-Heap 的 Greedy 策略恰好達到此目標。

### 回程 Queue 的現實意義

騎手從客戶端返回待命站需要物理時間，無法瞬間消失再出現。Queue 的 FIFO 結構模擬了這個現實：

- 先送完的騎手在 Queue 前方，先回到待命站
- 後送完的騎手在 Queue 後方，後回到待命站
- 回到待命站的瞬間，系統自動重新評估派單資格

### Idle 發生的條件

當所有騎手都在回程途中（Queue 非空但全部未解凍），且無新訂單可安排時，系統進入 Idle。這代表騎手數量不足或回程距離太遠，是平台應增派騎手的警示信號。

## 六、模擬器功能說明

### 可調整參數

| 參數 | 預設值 | 說明 |
|------|--------|------|
| 訂單數 | 15 | 本批次待配送訂單總數 |
| 騎手數 | 2 | 同時在外送中的騎手人數 |
| 回程冷卻 | 3 | 騎手送完後返回待命區的時間單位 |

### 顯示面板

| 面板 | 內容說明 |
|------|---------|
| Max-Heap 待派訂單 | 所有待派訂單依優先值排序，紅框標示當前最高優先 |
| 騎手回程 Queue | 顯示回程中的騎手與預計返回時間，綠框代表已返回 |
| 已送達訂單 | 成功送達的訂單清單，顯示商品名稱與省下的罰款 |
| Time Slot 序列 | 每個時間單位的派單或 Idle 狀態 |

### 統計輸出

- 總訂單數 / 已送達數
- 騎手閒置次數（Idle）
- 總省下罰款（總營收）

## 七、實際外送平台對應關係

```
演算法元件          外送平台實體對應
──────────────────────────────────────────────
Max-Heap 頂端    ↔  後台系統當下最危急的訂單
Heap Push        ↔  新訂單成立，自動加入排班佇列
Heapify Up       ↔  高罰款訂單自動搶至派單隊伍最前
Heapify Down     ↔  最高優先訂單派出後，次高順位浮頂
Queue FIFO       ↔  騎手返回待命站的先後物理順序
解凍條件         ↔  GPS 確認騎手已返回商圈待命半徑
Idle             ↔  「無可用騎手」警示（建議加派人手）
```

## 八、延伸思考：動態優先值更新

現實中，隨著時間流逝，訂單的緊急程度會動態上升（距離超時越來越近）。可設計「老化機制（Aging）」：

```
每過 1 個 time slot，所有待派訂單的優先值 += 老化加分
```

這樣可防止低優先值訂單因長期等待而被餓死（Starvation），確保每筆訂單最終都能被派出。

---

## 九、結論

外送派單問題將工業排程的核心邏輯帶入日常生活：Max-Heap 扮演「最佳化決策引擎」，永遠選出損失最小的派單選擇；Queue 扮演「物理資源回收帶」，確保騎手的使用符合現實時間限制。兩個資料結構的結合，使得有限騎手資源在複雜訂單流中發揮最大效益，是現代外送平台後台算法的核心思想。
